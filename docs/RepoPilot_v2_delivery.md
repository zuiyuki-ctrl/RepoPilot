# RepoPilot v2 阶段交付说明

更新：2026-10-17。定位：Coding Agent Evaluation & Experiment Platform。

## 一、目标用户与设计理念

RepoPilot 面向 Coding Agent 开发者、AI Infra 和评测团队，帮助回答三个问题：Agent 在哪一步出现问题？策略调整带来了哪些收益与退化？是否有足够证据采用新版本？核心理念是：**让 Coding Agent 的每一次改进，都有证据支持。**

平台将可观测、可评测、受控实验和人工决定连接起来。执行完成与验收通过独立保存；缺失数据保持未知；历史证据不由当前工作区重算；单次 Trace 提供排查线索，不自动证明根本原因。它不是新的代码编辑器，也不以“模型说完成了”作为任务成功标准。

## 二、已交付的功能闭环

前端可登记并校验 Agent/Benchmark 版本，预览冻结实验清单，启动批次、查看成员进度与 Run 详情，处理 Native 审批、取消运行，查看测试、Diff 和 Trace，比较策略并保存人工决定，下载 JSON/Markdown 报告。新增实时 Dashboard 汇总当前数据库状态；下载的 JSON 报告可重新上传只读核验，不导入实时实验、不重算成绩。

后端支持内置 Agent 的 Native Adapter，以及遵循 JSON 协议、使用本地不可变 Docker 镜像的外部 Process Adapter。实验固定 Case、源码提交、测试环境、预算和 Agent 版本；controlled 模式核对声明的配置差异，benchmark 模式允许多变量比较但不据此归因。准备失败、取消与待定成员均保留。原有仓库索引、代码问答、规划、受控候选生成/写入、沙箱测试与反思修复仍作为内置 Agent 能力存在。

真实例子：同一 task-list fixture，noop 的执行结果为 completed，但最终测试仍为 2 failed / 6 passed，所以验收不通过；fix 为 8 passed 且修改范围合法，验收通过。这证明平台能区分执行与质量，不能代表通用 Coding Agent 的成功率。

## 三、架构与证据管理

主要链路为：Vue 3 / TypeScript 页面 → FastAPI / Pydantic 接口 → 业务服务 → PostgreSQL / SQLAlchemy；持久 worker 领取准备、目录校验和 Run 工作，Native 复用 LangGraph 编排，Process 在受限容器中执行，平台独立采集基线与最终测试。

模型包含 Agent/Benchmark 版本、实验与成员、Run/工作状态/事件、TestRun、Evaluation 及人工决定。长时间模型或容器执行不持数据库行锁；领取和结算使用短事务、所有权 token 与执行栅栏。无法确认清理时禁止自动重放，避免重复执行。当前 worker 按单工作进程协调设计，不宣称具备分布式高并发调度。

配置、请求、评测和报告以内容 hash 绑定；比较/导出在同一数据库只读快照中完成。人工决定追加保存当时比较快照，不能覆盖机器成绩。报告重读检查内容及内层绑定，但 hash 不是作者签名。Process 不挂载宿主凭据或 Docker socket、不开网络；当前固定 Python/pytest 环境也不等于能防止任意恶意被测代码作弊。

## 四、如何观测、量化与作出决定

**观测：** L0 关注执行、测试和产物；L1 增加模型/工具调用及用量；L2 增加检索、实际上下文、计划和反思等过程证据。层级表示可观测深度，不是 Agent 质量分。页面区分缺失、部分、未发生和不支持，并标识外部自报来源、截断与异常；能力声明不等于证据已采集。

**召回算法：** Python AST 分块后，使用 Embedding 与 pgvector 余弦距离检索；关键词检索用 PostgreSQL `simple` 全文搜索，覆盖路径、符号和源码。Hybrid 两路各取最多 20 个候选，按代码块 ID 合并，以 `Σ 1/(60 + rank)` 的 RRF 分数排序后取 top_k。关键词当前没有中文分词，多词 AND 匹配，因此不保证 Hybrid 优于 Vector。标注检索集的 Recall@K 为“前 K 条命中的期望代码块数 / 期望代码块总数”，与端到端任务成功率分开。

**任务与资源量化：** 平台按冻结规则、保护测试、修改范围和绑定快照独立验收。实验按 Case × repetition 配对，列出改善、退化、双方通过/不通过、待定和不可比；已启动分母与可比对子分母分别展示。成对通过率差为 `(改善数 − 退化数) / 可比对子数 × 100` 个百分点。Token 仅在调用覆盖和归属充分时作为完整总量，部分数据只列已知小计；资源比较使用双方均有数据的同一组对子。墙钟包含等待和平台验收，不能直接当模型推理耗时；没有历史价格就不输出假成本。

**决策算法：** 使用预先冻结的确定性质量门槛：最少对子、最少不同 Case、最多退化、最低通过率差。证据不足则不判达标，旧实验不补造门槛。人工可选择采用、保留或继续实验，并记录理由及所依据的快照。它不是训练出的决策模型，也不自动签发发布许可。

## 五、验证范围与可扩展方向

本轮 Day 1—7 离线回归 **141 项通过**，已有前端快照测试 **21 项通过**，类型检查及生产构建通过；真实数据库总览和已有报告重读通过，篡改报告返回 422。此前已完成 noop/fix、错误身份、超时、保护测试篡改、越界修改等真实 Docker fixture 验证。本轮未调用模型/Embedding、未重跑容器、无新增迁移。最新 Dashboard/报告页仍待浏览器目视；新的 Native 真实模型批次及浏览器完整新建流程未由上述检查覆盖。数据库 head 为 `d716a06b0001`。

目前交付定位是本机可信操作者使用的平台 MVP，不是任意 Agent 拖入即运行的通用 SaaS。优先扩展外部 Agent SDK 与真实模型接入、受控网络/凭据、完整调用覆盖证明；随后补价格快照与资源门槛、完整原始证据包、CI 回归、权限隔离及更多测试环境。策略方向可研究 Reranker、上下文筛选和恢复策略，但要用版本化任务集与受控重复实验验证收益和代价，不预设提升。
