# RepoPilot 七天实验工作台交付计划

周期：2026 年 10 月 7 日—10 月 13 日

计划修订：2026 年 10 月 7 日

## 一、项目定位与本周唯一目标

RepoPilot 是一个可观测、可评测、可实验的 Coding Agent 基础设施与研究平台（Agent Harness + Evaluation Infrastructure）。

代码问答、Bug 修复和小功能开发是评测任务与演示载体，不是项目差异化的全部。项目重点是回答：Agent 使用了什么上下文、采取了哪些动作、在哪一步失败，以及策略变化是否带来了可核查的收益与代价。

差异化不建立在“成熟产品没有 Trace 或评测能力”之上，而建立在具体代码任务、可控实验条件、可追溯证据和诚实结论之上。这是回到《RepoPilot_PRD_v1.1.md》第 20～24 节的研究主线，不是推倒已有工程重新开发。

本周唯一目标：交付一个最小 Coding Agent 实验工作台，让同一批固定任务在两种受控配置下独立运行，展示逐例结果，并追溯到检索、实际上下文、计划、修改和测试证据。

边界：保留人工批准、分阶段执行、有界重试；不声称已经实现通用全自动修复。可复现首先指输入、配置、环境和证据可核查，不保证模型每次输出完全相同。

## 二、当前基础与关键缺口

以下是制定计划时的进度基线，不代表本周功能已经完成，也不代表最新测试已经通过。后续以实际代码与验收记录为准。

| 已有能力 | 在实验工作台中的作用 |
|---|---|
| Vector / Keyword / Hybrid、检索对照报告 | 可替换、可比较的检索策略 |
| 计划、人工审批、受控修改 | 被研究的执行流程 |
| Docker 测试、源码快照、TestRun | 执行环境与修改结果证据 |
| Reflection、重试预算、终止事件 | 可观察的失败恢复机制 |
| 历史报告、JSON / Markdown 导出 | 可复查的实验材料 |

关键缺口：

1. 当前模型可以在 search_code 调用时选择策略，但缺少运行级策略锁定。“能选择策略”不等于“能做对照实验”。
2. 检索工具事件已有策略和命中数量，但还不足以关联完整查询、排序结果，以及预算处理后真正交给模型的上下文。
3. 检索级对比已经存在；完整任务的配置、运行、测试和结果尚需统一串联，不能把 Recall 当成任务成功率。
4. 本周需要最小的实验汇总与失败证据链，而不是重新实现已有报告、测试和事件系统。

## 三、本周冻结范围与实验约定

### 3.1 最小实验规模

- 一个自研 Agent 后端。
- 两种运行配置：固定 Vector 与固定 Hybrid。
- 三个小型代码修改用例，覆盖 Bug 修复与小功能开发；优先使用独立的小型 Python 样例仓库，不让 RepoPilot 自身承担全部演示。
- 每个用例在两组配置下各运行一次，形成至少六条真实运行记录。失败、拒绝和环境错误也保留，不通过只展示成功记录美化结果。
- 现有检索数据集继续使用，检索 Recall 与端到端任务结果分开报告；代码问答能力保留，不额外扩展为本周独立产品主线。

这是验证平台能力的小规模演示，不足以宣称通用成功率或统计显著提升。

### 3.2 只改变一个实验变量

两组只改变检索策略，固定或明确记录：

- 用例版本、仓库初始 commit、验收与回归测试版本。
- 模型、生成参数、提示词版本、Embedding 与索引版本。
- Docker 测试镜像与依赖环境。
- 工具调用、上下文、超时和重试预算。
- 人工审批规则与实际介入情况。

本周两组沿用同一套恢复规则，最多追加一轮修复；具体配置随运行保存。若沿用现有 Reflection，就使用明确的配置名称，不冒充 PRD 中采用 Simple Retry 的 B0 / B1。

每次运行从固定初始状态创建独立工作区；上一组修改不能进入下一组。验收测试预先固定并受保护，不能靠删除、放宽或修改验收条件获得通过。

人工审批不能偷偷演变为给某组补答案。额外提示或人工改代码必须记录为干预，不与未干预运行混为同一口径。

### 3.3 自由模式与实验模式分开

- 自由模式：保留模型自主选择 Vector / Keyword / Hybrid 的现有能力。
- 实验模式：运行开始时固定检索策略，由服务端执行约束，不仅依靠提示词；策略约束贯穿该运行中实际发生的检索调用。
- 保存实际生效配置，不能只记录用户希望使用的配置。

| 第 3 天：10/9 | 单次实验结果闭环 | 一个真实用例能串起运行配置、任务、测试记录、终态和历史报告；结果如实保存，执行失败也有可定位记录，不要求靠人工修正模型答案来达成闭环。 |

| 第 7 天：10/13 | 复跑、演示与交付 | 按 README 从固定起点复跑代表性用例，保留新旧运行记录；整理配置、真实报告、结论和限制，形成 5～10 分钟演示流程。只处理交付阻断，不临时扩展功能。 |

## 五、证据与失败分析规则

### 5.1 需要回答的问题

每次实验至少能够追溯：

1. 使用哪个用例、初始源码和实际运行配置？
2. 发出了什么检索查询，使用什么策略，返回哪些有序候选？
3. 哪些结果真正送入模型，哪些因预算被丢弃？
4. 生成了什么计划，发生了哪些审批、工具调用与文件修改？
5. 对应哪个 TestRun，测试结果是什么，是否发生重试？
6. 最终成功、失败或停止的依据是什么？

复用 task_events 作为任务轨迹的权威持久化来源，实验汇总保存配置、结果和证据引用，不另造一套与任务事件冲突的事实来源。报告沿用历史事件与测试关联，不重新读取当前工作区来替代历史证据。

检索候选与实际模型上下文必须区分。记录可观察动作、输入输出摘要、内容 hash 或受控快照引用，不要求或伪造模型内部思维链。凭据脱敏，大段内容使用受控 artifact。

### 5.2 失败分类

沿用 PRD 第 22 节，不另创一套含义冲突的标签：

- 每个失败运行有一个主要类别，可附次要原因。
- 保存关联事件、测试或修改证据，以及分类来源、复核状态和说明。
- 断言失败不自动归为 TEST_FAILURE；该类别用于测试基础设施、依赖、收集或容器问题。
- 未命中某文件不自动证明 RETRIEVAL_FAILURE 是任务失败根因，需要核验该文件是否必要。
- 模型生成的诊断是待核验假设，不是已证实根因；证据不足记录 UNKNOWN。
- 不强求自然失败数量；若无真实失败，诚实记录。需要验证失败路径时可以使用明确标注的故障注入，但不混入自然运行成功率。

### 5.3 当前搜索问题作为首个分析案例

已观察到部分自然语言查询与明确函数名查询的关键词搜索表现不同，先前 Vector / Hybrid 对照也没有显示 Recall 提升。分析顺序固定为：

1. 关键词分支是否有候选？
2. 有候选时，是否进入融合后的 Top-K？
3. 进入 Top-K 后，是否真正交给模型？
4. 上下文变化后，计划与最终结果是否变化？

不能从一个空结果泛化为所有查询都失败，也不能把“最终列表没有关键词贡献”等同于“关键词分支完全没有候选”。本周先建立证据链，不把中文分词或查询改写插入开发主线。

## 六、验收与里程碑

### 第三天里程碑

至少一条真实运行完成“配置 → 任务 → 执行 → 测试或明确失败 → 结果报告”的闭环。人工批准和操作有记录，不宣称全自动执行。

### 第七天验收

- 三个固定用例、两种受控配置和至少六条真实运行记录可查询；代表性用例可按说明重新运行。
- 能逐例对比结果，而不只展示一个汇总成功率。
- 能从单次结果定位相关检索、上下文、修改、测试和终止证据。
- 展示已有可可靠采集的耗时、调用和重试信息，注明统计范围；人工等待与执行耗时不混为未说明的单一指标。
- Token、成本或测试数量未采集到时明确标记缺失，不填零或根据文本长度伪造；存在估算时说明估算口径，不冒充实际用量。
- 失败有证据支持的分类或明确的 UNKNOWN；没有改善也交付真实分析，不以 Hybrid 必须获胜作为验收条件。
- 集中验证策略锁定、工作区隔离、拒绝审批不能写入、旧测试不能完成任务、预算到限停止，以及只读报告恢复不会重复执行写操作。
- README、配置说明、真实报告和已知限制足以支持本地演示。

本周是研究平台的最小可演示切片，不等于完成 PRD 的全部月底验收。完整 B0 / B1 / B2、扩大数据集和 eval_cases / eval_runs 持久化要求仍需独立跟踪；若本周以文件保存最小实验记录，须明确记录为阶段性实现，不能声称数据库要求已交付。

## 七、本周不做与后续方向

本周不做：

- AST 依赖扩展、Reranker、中文分词、查询改写、大规模检索调参。
- 五十个任务、四种上下文策略或完整 B0 / B1 / B2 实验矩阵。
- Codex、Claude Code、OpenCode 等多个外部 Agent 接入。
- 多 Agent、通用自主执行引擎、通用崩溃恢复、长任务规划和后台任务队列。
- 登录、多用户、云部署、复杂前端框架、高级交互式 Trace Viewer。
- 与本周实验闭环无关的抽象、重构和监控扩展。

后续方向保留：外部 Agent 适配、统一评测协议、扩大及划分数据集、重复实验、更多上下文策略、Simple Retry 与 Reflection 的等预算对照。外部 Agent 对比必须说明模型、权限、预算和可观测程度的差异，不能把接通几个命令行等同于公平比较。

## 八、执行纪律与下一步

- 每次开发先说明当前处于哪一天、这一轮交付什么、还差什么。完成一项就记录证据，不因为跨电脑开发重新从头规划。
- 先解释模块用途和数据流，再给具体到文件、函数与参数来源的编号骨架；由用户实现，随后检查。发现问题同时解释原因和修改方式，不只贴答案，也不只给函数签名。
- 每轮交付一个完整小功能，不再按两三个字段零散推进。
- 前五天做必要的局部检查，第三天验证首次真实闭环，第六天集中联调，第七天排练；不为每个方法单独安排一批测试。
- 审批、写入范围、实验隔离、测试依据和重试上限的明显错误立即处理，不能为了赶进度绕过安全边界。
- 不自动批准任务，不在网络超时后盲目重发写请求，不擅自启动付费模型批量实验。
- 保留原始结果与失败记录；静态检查、模拟测试、真实联调和历史报告明确区分，未执行的验证不能声称通过。
- 新想法统一进入后续待办，不插入本周主线。如有阻断，先说明影响与最小修复；改变范围或日期须由用户确认。
- 进度紧张时优先减少页面装饰与非必要统计图，不删除固定验收、独立工作区、策略控制和证据关联。

下一步固定为：运行级实验配置与检索策略锁定模块。先建立可靠的实验变量，再向下连接执行、证据与展示，不先做聊天页面。

最终演示要回答的不是只有“它能修一个 Bug”，而是：同一个任务在两种受控策略下看到了什么上下文、产生了什么修改、获得了什么测试结果，以及这些证据支持和不支持哪些结论。
