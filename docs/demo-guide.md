## 三段演示

### 1. 总览：说明任务与证据（约 1 分钟）

打开“实验总览”，指出三个固定用例、两种检索策略、六条主运行，以及额外的准备错误和未完成记录。

可以这样介绍：“RepoPilot 不只是让模型给一份代码答案。我把规划、人工审批、候选、实际写入、容器测试和最终报告拆成可追溯的步骤。这个页面展示已保存的历史结果，不是实时运行状态。”

补充一句：两组每次从固定源码提交创建独立工作副本，固定验收测试受保护。它们是小规模开发集，不是生产仓库基准。

### 2. 对比：解释为什么保存检索轨迹（约 2～3 分钟）

打开“策略对比”，定位 **deduplicate / v1**，展开双方“查询与命中”。

- Vector 首次查询含自然语言，返回的 Top 5 都是测试；第四次查询才出现实现，排第 1。不要把检索次数直接解释成算法普遍优劣。
- Hybrid 首次查询 `deduplicate_by_key`，实现排第 4；找到双方共有的查询 `deduplicate.py`，实现的向量排名 7、关键词排名 1、融合排名 3。关键词帮助它进入该次 Top 5。
- 两组最终都通过固定测试，因此本批没有显示任务成功率差异；其他查询不同，也不能把所有排名差异归因于 RRF。

展开“工具上下文”：`accepted` 表示结果进入消息历史，关联模型请求说明后续请求携带了它，不表示模型一定正确使用了内容。task-list 的旧 Vector 没有新版轨迹，页面写“未记录”，不能讲成没有检索。

### 3. 详情：从建议追溯到实际结果（约 3 分钟）

进入 **deduplicate / Hybrid** 的“查看运行详情”。固定实验 ID：`6ce17de7-ad33-4232-bac6-5c1d673d326d`；任务 ID：`a2574e05-f9a8-4257-94b9-c6d4153d4f61`。

沿时间线查看计划、审批和候选，再选历史报告查看 Diff 与 TestRun：

- 计划是准备怎么改，批准表示允许进入执行；候选仍只是待应用的完整文件内容。
- 最终 Diff 仅修改 `deduplicate.py`：读取键值后，仅当键尚未出现才写入映射，保留首次记录和插入顺序。
- TestRun `ef9d2f9c-a41b-4e78-92e4-6a526c8c668a` 保存 `exit_code=0`、`6 passed in 0.08s`，任务最终 completed，retry_count=0。0.08 秒是 pytest 输出时间，不是 Agent 总耗时。
- 历史报告绑定测试记录、快照标识和保存的 Diff，不会用当前工作区的新内容替换历史结果。

## 面试中值得亲自讲清楚的三个问题

**为什么候选生成与写入分开？** 模型输出可能格式正确但语义错误。生成阶段不修改文件，应用阶段复核批准计划、范围和原文件 hash；如果期间文件变了，就不能把旧候选直接覆盖上去。

**为什么同时保存 TaskEvent 和 TestRun？** TaskEvent 回答“按什么顺序发生了什么”，TestRun 回答“这一轮测试使用哪个环境、针对哪个快照、得到什么结果”。事件 sequence 用于同一任务内的顺序和关联，TestRun ID 标识具体测试，两者不能互相替代。旧测试通过不自动证明后续写入后的代码通过。

**为什么还需要 scripts？** scripts 处理命令参数和本地实验文件，services 处理业务条件、事务和编排。实验与 HTTP 共用业务服务，避免各写一套审批、写入和完成逻辑。前端目前消费离线报告，适合无数据库环境的演示。

建议自己用五分钟讲一遍这三个问题，并从界面指出对应证据；这比照读实现细节更能体现你对项目的掌握。
